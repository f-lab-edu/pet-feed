# 2026-10-22 개발 상태

## 작업 범위

회원 등록, 로그인, 프로필 조회, 회원 수정, 회원 탈퇴를 구현하고 핵심 규칙을 새 테스트로 검증했다. 기존 테스트는 요구사항의 기준으로 사용하지 않았고, 회귀 확인을 위해 마지막 실행에는 포함했다.

## 구현 상태

| 기능 | API | 성공 상태 | 주요 동작 |
| --- | --- | --- | --- |
| 회원 등록 | `POST /api/v1/users/signup` | 201 | 이메일 중복 방지, BCrypt 해시 저장, 회원 키·등록 시각 반환 |
| 로그인 | `POST /api/v1/auth/login` | 200 | 이메일·비밀번호 검증 후 액세스 JWT 발급 |
| 프로필 조회 | `GET /api/v1/users/{user-key}` | 200 | 공개 프로필 조회, 비밀번호·해시 미노출 |
| 회원 수정 | `PUT /api/v1/users/{user-key}` | 204 | 본인 이메일·소개 수정, 다른 회원의 이메일 사용 금지 |
| 회원 탈퇴 | `DELETE /api/v1/users/{user-key}` | 204 | 본인 회원 데이터 삭제, 이후 조회·로그인 실패 |

- JPA `Member` 엔티티와 `MemberRepository`, `DefaultUserService`를 추가했다.
- 이메일은 소문자로 정규화한다. DB 유니크 제약으로 중복 저장도 방지한다.
- 수정 시 전달하지 않은 이메일·소개는 유지한다. 소개에 빈 문자열을 보내면 내용을 비울 수 있다.
- 이메일 변경 후 기존 이메일로 로그인할 수 없고, 새 이메일로 로그인할 수 있다.
- 잘못된 입력은 400, 로그인 실패는 401, 타인 수정·탈퇴는 403, 없는 회원은 404, 이메일 중복은 409로 처리한다.
- Facade에서 수정·탈퇴 요청의 `X-User-Key`를 user-service로 전달한다.
- Facade에서 하위 서비스의 오류 상태를 보존하고, 유효한 HTTP 상태가 없는 통신 오류는 502로 처리한다.
- 기존 회원가입 통합 테스트의 기대 상태만 새 계약인 201에 맞췄다.

## 문자열 상수 관리 결정

커스텀 HTTP 헤더 이름은 서비스 간 계약이므로 공통 상수로 관리한다.

- `MyHttpHeaders`를 Facade의 `config` 패키지에서 `common-domain`의 `com.petfeed.domain.http` 패키지로 옮겼다.
- 기존 공통 DTO와 같은 공유 계약 모듈에 두어 Facade·Gateway·user-service 사이에 새 의존성을 만들지 않았다.
- Java 최상위 클래스는 `static`으로 선언할 수 없으므로 `final` 클래스, `private` 생성자, `public static final` 필드로 구성했다.
- Gateway·Facade·user-service의 운영 코드에서 `X_USER_KEY`를 사용한다.
- 사용하지 않는 `USER_KEY`는 제거했다. 경로 변수 이름은 HTTP 헤더 상수에 포함하지 않는다.
- 표준 `Authorization` 헤더에는 Spring의 `HttpHeaders.AUTHORIZATION`을 사용한다.
- 오류 메시지, URL 경로, 모든 문자열을 한곳에 모으지 않는다. 같은 의미의 계약을 공유할 때만 상수화를 적용한다.
- HTTP 테스트는 외부 계약 문자열을 직접 사용해 상수 값이 잘못 변경되는 경우도 검출할 수 있게 유지했다.

## 제한 사항과 다음 작업

- 현재 DB 설정은 메모리 H2와 `create-drop`이다. 서비스 재시작 시 데이터가 보존되지 않는다.
- 수정 범위는 기존 DTO의 이메일·소개다. 닉네임·전화번호·비밀번호 변경은 구현하지 않았다.
- 탈퇴는 물리 삭제다. 재가입 제한, 보존 정책, 연관 데이터 정리는 별도 정책이 필요하다.
- 로그인 응답의 `refreshToken`은 `null`이다. 갱신·로그아웃·탈퇴 시 기발급 JWT 즉시 폐기는 구현하지 않았다.
- 수정·탈퇴 권한은 내부 `X-User-Key`가 Gateway에서 신뢰할 수 있게 전달된다는 전제다. 내부 서비스 직접 접근 차단과 헤더 위조 방어를 별도로 검증해야 한다.
- Gateway를 포함한 전체 E2E는 실행하지 않았다. Gateway 기동·JWT 검증·프록시 동작을 검증하는 테스트가 다음 단계다.
- Facade 프로필 조회는 기존대로 post-service의 게시물 수 조회에 의존한다. 이번 H2 테스트는 user-service를 직접 검증한다.
- 게시물·팔로우·팔로잉의 비즈니스 기능은 이번 범위에 포함하지 않았다.
