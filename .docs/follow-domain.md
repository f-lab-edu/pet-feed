# 팔로우 도메인 명세

- 기준일: 2026-10-30. 현재 작업 브랜치의 구현 기준이다.
- 소유 서비스: `follow-service`, `com.petfeed.follow`, H2 `followdb`, 포트 8085.
- 회원·게시물·댓글 엔티티나 DB를 참조하지 않는다. 회원 식별자는 문자열 논리 참조다.

## 모델과 관계

| 컬럼 | 타입 | 제약 |
| --- | --- | --- |
| id | Long | 자동 증가 PK, 목록 커서 기준 |
| follower_key | String | 팔로우하는 회원, 필수·변경 불가 |
| following_key | String | 팔로우받는 회원, 필수·변경 불가 |
| created_at | LocalDateTime | 생성 시 서버 로컬 시각, 변경 불가 |

- `follows` 테이블의 `(follower_key, following_key)` 유니크 제약으로 중복 및 동시 중복 요청을 방지한다.
- 도메인 검증과 DB CHECK로 자기 팔로우를 금지한다. 양쪽 회원 키는 공백 불가, 최대 255자다.
- `(follower_key, id)`, `(following_key, id)` 인덱스를 둔다.
- A → B와 B → A는 서로 다른 관계다. 맞팔이 자동 생성되지 않는다.
- 언팔로우는 요청자 → 대상 관계만 물리 삭제한다. 없는 관계의 언팔로우도 성공한다.

## API와 책임

| 외부 API | 동작 |
| --- | --- |
| POST /api/v1/following/{user-key} | 요청 회원이 대상을 팔로우. 성공 200, 중복 409, 자기 팔로우 400 |
| DELETE /api/v1/following/{user-key} | 요청 회원이 대상 언팔로우. 관계 유무와 무관하게 성공 200 |
| GET /api/v1/users/{user-key}/followers?cursor=0 | 정상 회원 팔로워 목록 |
| GET /api/v1/users/{user-key}/followings?cursor=0 | 정상 회원 팔로잉 목록 |
| GET /api/v1/users/{user-key} | 실제 팔로워·팔로잉 수, 요청자 기준 following 여부를 프로필에 조합 |

- Gateway의 JWT 인증과 X-User-Key 전달을 사용한다. 요청자 식별자는 클라이언트 본문에서 받지 않는다.
- Facade가 두 회원의 존재·정상 상태를 확인한 후 생성한다. 탈퇴 회원은 403, 없는 회원은 회원 서비스의 404를 전파한다.
- 목록·프로필 집계도 요청자와 조회 대상의 정상 상태를 요구한다. 언팔로우는 요청자의 정상 상태만 확인하므로 탈퇴 대상과의 관계를 제거할 수 있다.
- follow-service는 방향·입력·중복·페이지 규칙과 데이터만 소유한다. 회원 상태 확인은 Facade 책임이다.
- follow-service의 내부 목록은 상대 회원 키와 관계 ID만 반환한다. Facade가 현재 닉네임, profileImageUrl=null 및 요청자 기준 following 여부를 조합한다.
- `GET /internal/v1/users/{key}/followers`, `/followings`는 관계 ID 내림차순 20개 목록이다.
- `GET /internal/v1/follows/targets?requester=...&keys=...`는 최대 20개 대상 중 요청자가 팔로우한 회원 키 집합을 반환한다.

## 탈퇴, 커서와 집계

- 탈퇴 시 원본 팔로우 관계를 보존한다. 탈퇴 처리에 follow-service의 분산 삭제를 추가하지 않는다.
- 외부 목록과 프로필 수는 현재 회원 상태를 조회해 WITHDRAWN 관계를 제외한다. 프로필 수는 정상 상대 회원 관계 수이며 원본 테이블 행 수와 다를 수 있다.
- 목록은 내부 페이지를 계속 읽어 정상 회원 최대 20명과 다음 정상 회원 1명을 찾는다. 다음 페이지가 있으면 마지막 반환 관계 ID를 nextCursor로 제공한다. 탈퇴 회원이 한 페이지 전체를 차지해도 뒤의 정상 회원을 건너뛰지 않는다.
- 최초 cursor=0, 이후 id < cursor, 음수는 400이다. 마지막 nextCursor=null, hasNext=false다. 커서는 회원 키나 페이지 번호가 아니다.
- 작성자 상태는 한 요청 안에서 캐시한다. 회원 조회 실패를 탈퇴로 해석하거나 집계 실패를 0으로 숨기지 않는다.
- 현재 집계는 관계 전체를 20개씩 스캔해 회원 상태를 확인한다. 정확한 현재 상태 반영을 우선한 초기 구현으로, 관계 수에 비례한 HTTP 호출 비용이 있다. 규모가 커지면 회원 상태 일괄 조회 또는 이벤트 기반 상태 투영 및 집계로 교체해야 한다.

## 한계와 검증 범위

- 상태 확인 직후 탈퇴하는 동시 요청의 원자성이나 목록·집계 전체의 단일 시점 스냅샷은 보장하지 않는다. 뒤에 조회하는 목록·집계는 탈퇴 관계를 제외한다.
- 기존 회원 레코드 보존 정책을 전제한다. 물리 삭제로 회원 참조가 깨지면 조회 오류를 전파한다.
- 내부 서비스 접근 통제와 JWT 즉시 폐기는 별도 작업이다. follow-service 직접 호출은 Facade의 회원 검사를 우회할 수 있다.
- H2/create-drop으로 재시작 시 관계가 사라진다. 운영 DB 마이그레이션과 영속화는 미구현이다.
- 임시 화면에 팔로우 버튼·목록 UI는 추가하지 않았다. HTTP 예제와 기존 API를 통해 사용할 수 있다.
