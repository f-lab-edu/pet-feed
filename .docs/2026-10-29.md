# 2026-10-29 개발 상태

## 댓글 도메인 서비스 분리

- 도메인별 서비스 분리 방향에 맞춰 `services/comment-service`를 신설했다. Spring Boot 애플리케이션, Gradle 모듈, `com.petfeed.comment` 패키지와 H2 `commentdb`, 포트 8084를 사용한다.
- 댓글 엔티티·저장소·서비스·컨트롤러와 테스트를 post-service에서 이동했다. `Comment`는 `Post` JPA 참조 대신 `Long postId`를 저장하며 게시물 DB 외래 키나 서비스 모듈 간 Gradle 의존성을 두지 않는다.
- 외부 댓글 API 경로와 요청·응답은 유지한다. CommentFeignClient는 `services.comment-service.url`로 연결한다. Facade가 댓글 작성·조회·수정·삭제 전에 게시물 존재를 확인한다.
- 댓글 수는 comment-service의 내부 일괄 조회 API를 통해 Facade에서 조합한다. 게시물 페이지당 최대 20개 ID에 대해 한 번 호출하며 댓글이 없는 ID는 0으로 처리한다. 댓글 수 조회 실패를 0으로 숨기지 않는다.

## 게시물 삭제 조정과 부분 실패

1. Facade에서 정상 회원과 게시물 작성자 권한을 확인한다. 타인 요청은 댓글을 건드리기 전에 403으로 거절한다.
2. comment-service의 내부 삭제 API로 해당 게시물의 댓글 작성을 차단하고 기존 댓글을 삭제한다.
3. 성공하면 post-service에서 게시물을 삭제한다.

- comment_threads에 게시물별 차단 상태를 남기고, 댓글 생성과 차단·삭제가 동일 행의 DB 잠금을 사용한다. 차단 전 완료된 생성은 삭제 대상이 되고 차단 후 늦게 도착한 생성은 404로 거절한다.
- 차단·삭제는 댓글 DB 트랜잭션이며 멱등적이다. 댓글 정리 실패 시 게시물 삭제는 시도하지 않는다.
- 정리 성공 후 게시물 삭제 실패 시 댓글은 이미 삭제되고 작성이 차단돼 있다. 게시물은 남을 수 있으며 같은 삭제 요청을 수동 재시도해 마무리한다. 되돌리기·자동 복구 작업과 서비스 간 원자성은 제공하지 않는다.
- 게시물 삭제 성공 응답이 유실된 경우 재시도는 게시물 조회 404가 될 수 있다. 내부 post-service를 직접 호출하는 삭제는 댓글 정리를 우회하므로 내부 서비스 접근 통제가 필요하다.
- 기존 H2/create-drop을 유지한다. 댓글 서비스 단독 재시작으로 댓글 및 차단 이력이 사라지는 한계가 있으며 영속화가 후속 작업이다. 기존 댓글 데이터 이전 스크립트는 제공하지 않는다.

## 검증

- 실행: `.\gradlew.bat :comment-service:test :post-service:test :facade:test :api-gateway:test :user-service:test --console=plain` → BUILD SUCCESSFUL.
- 결과 파일 기준 comment-service 5개, post-service 6개, Facade 44개, Gateway 2개, user-service 19개로 총 76개 테스트 실패/오류 0이다. 최종 실행에서 변경 없는 댓글·게시물 테스트는 이전 통과 결과를 재사용했다.
- 댓글 독립 DB의 CRUD·권한·페이지·일괄 count, 반복 정리와 늦은 생성 차단, 최초 생성과 삭제의 동시 실행을 검증했다.
- Facade에서 게시물 존재 확인 순서, 타인 삭제 차단, 정리 실패 시 게시물 유지, 게시물 삭제 실패 후 재시도, 댓글 수 조합·조회 실패 전파를 검증했다. WireMock으로 댓글 생성의 요청·사용자 키 및 내부 정리 API 전달도 확인했다.
- 중간 실행에서 새 계약 테스트의 메서드 import 충돌을 수정했다. 이후 기존 회원 계약 테스트 한 건에서 502 연결 오류가 발생했으며, 최종 전체 실행에서는 재현되지 않았다. 반복 발생 여부는 후속 관찰이 필요하다.
- `git diff --check` 통과. 실제 다섯 서비스 전체 기동 및 브라우저 E2E, 운영 DB 검증은 이번 작업에서 수행하지 않았다.
