# 홈 피드 알고리즘 v1

## 목적과 책임

팔로우한 회원의 소식과 아직 팔로우하지 않은 회원의 글을 함께 보여준다. Gateway 인증 → Facade의 FeedFacade → 각 소유 서비스의 조회 API를 사용한다. 별도 피드 서비스나 메시지 브로커는 도입하지 않는다.

- post-service: 최근 30일, 삭제되지 않은 본인 외 게시글 중 ID 내림차순 최대 500개 후보 조회. 선택된 ID 최대 10개의 최신 본문·첨부 일괄 조회.
- follow-service: 후보 작성자의 팔로우 여부를 기존 targets API로 20명씩 확인.
- Facade: 후보 순서 계산, 탐색 세션 관리, 작성자·댓글 수 조합.
- 화면: 로그인과 홈 버튼에서 홈 피드 조회. 내 기록·회원 검색은 기존 회원별 목록 사용. 데모 모드는 기존 로컬 데이터 유지.

## 순서와 배합

1. 팔로우 후보는 작성 시각 내림차순, 동률이면 ID 내림차순.
2. 발견 후보는 `0.6 × exp(-ageDays / 7) + 0.4 × seededRandom` 점수 내림차순. ageDays는 후보 중 최신 글과의 차이이며 임의 시드와 게시글 ID로 난수를 고정한다. 동률이면 ID로 순서를 고정한다.
3. 10개 슬롯 중 3·6·9번째에 발견 글을 배치한다. 다른 슬롯은 팔로우 글을 우선한다.
4. 같은 작성자가 직전 글과 겹치면 해당 풀의 다른 작성자를 우선한다. 없으면 다른 풀의 작성자를 찾고, 양쪽 모두 없을 때만 연속 노출한다.
5. 후보 부족 시 다른 풀로 채운다. 따라서 **7:3은 목표 비율**이며 후보 부족·작성자 다양성 규칙 때문에 달라질 수 있다. 팔로우가 없으면 전부 발견 글이다.

## API와 페이지 일관성

`GET /api/v1/feed` — 로그인한 정상 회원만 허용. 새 요청마다 새로운 난수 시드와 후보 스냅샷을 생성한다.

`GET /api/v1/feed?cursor=<nextCursor>` — 반환받은 커서를 그대로 URL 인코딩하여 전달한다.

응답:

```json
{
  "items": [
    {"post": {"postId": 1, "memberKey": "author", "content": "hello", "author": {"status": "ACTIVE", "displayName": "친구"}}, "commentCount": 2, "source": "FOLLOWING"}
  ],
  "nextCursor": "세션UUID:10",
  "hasNext": true
}
```

- source: FOLLOWING 또는 DISCOVERY. 팔로우 여부는 첫 요청 시점 기준이다. 중간에 바뀐 관계는 새로고침 후 반영한다.
- 스냅샷은 순서·후보 메타데이터만 보관하며 콘텐츠는 매번 재조회한다. 같은 커서를 재요청하면 같은 슬롯을 읽는다. 수정한 글·댓글 수는 최신 값으로 바뀔 수 있다.
- 페이지당 최대 10개 슬롯을 소비한다. 중간 삭제된 글은 제외하므로 응답은 10개보다 적거나 비어 있을 수 있다. 다음 페이지 여부는 items 개수가 아니라 hasNext로 판단한다.
- 새 게시글은 기존 탐색에 끼워 넣지 않는다. 다음 새로고침에서 수집한다. 한 탐색의 서로 다른 페이지에 같은 글을 중복 배치하지 않는다.
- 커서는 사용자에 귀속된다. 잘못된 형식·오프셋은 400, 다른 사용자의 커서는 403, 만료·유실된 세션은 410이다. 410이면 새로고침으로 시작한다.
- 탈퇴 회원의 과거 콘텐츠는 기존 정책대로 보존하고 탈퇴 작성자로 표시한다. 하위 서비스 장애는 빈 피드로 숨기지 않고 오류로 전달한다.

## 현재 한계

- Facade 프로세스 메모리에 최대 1,000개 세션, 생성 후 15분 보관. 용량 초과 시 가장 오래된 세션부터 제거한다. 재시작·제거된 세션은 410이다. 다중 인스턴스 운영에는 공유 저장소가 필요하다.
- 전체 최신 500개 후보 밖의 팔로우 글은 첫 버전에서 놓칠 수 있다. 데이터가 커지면 팔로우 후보와 발견 후보를 저장소에서 각각 수집하는 방식으로 확장해야 한다.
- 영구적인 열람 이력, 개인 취향 학습, 좋아요 기반 순위, 신고·차단 필터는 아직 없다. 새 세션에서는 전에 본 글이 다시 나올 수 있다.
- 기존 게시글의 LocalDateTime 계약을 따른다. 서비스 간 시간대 통일은 별도 작업이다.
- 새로고침 시 순서가 달라질 수 있지만 후보가 적으면 같을 수 있다.
