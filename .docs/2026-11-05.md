# 2026-11-05 작업 기록

## 게시물 삭제와 댓글 정리 복구

도메인별 서비스 분리를 유지하면서 먼저 게시물 삭제의 부분 실패를 개선했다. 팔로우 조회 구조 변경은 다음 작업으로 남긴다.

### 변경 이유와 보장

- 기존 `댓글 정리 → 게시물 삭제` 동기 호출은 뒤 단계가 실패하면 댓글만 사라진 게시물을 남겼다.
- 이제 post-service가 소유권을 검사하고 `posts.deleted=true`와 `comment_cleanup_tasks`를 같은 DB 트랜잭션에 저장한다. 커밋 후 상세·목록·개수에서 게시물을 제외한다.
- Facade는 정상 회원 확인 후 삭제를 전달한다. 삭제 전 게시물 조회와 댓글 정리 호출은 제거했다.
- 삭제 행은 보존한다. 정상 회원인 원 작성자의 반복 삭제는 204이며 작업을 중복 생성하지 않는다. 타인은 403, 없는 게시물은 404다. 삭제한 게시물의 상세·수정은 404다.
- 삭제는 게시물 행 잠금으로 직렬화한다. 버전 필드로 동시에 시작한 수정이 삭제 상태를 덮어쓰는 것을 방지한다.

### 댓글 정리 작업

- 작업 필드: `postId` PK, `nextAttemptAt`(Instant), `attempts`.
- 기본 5초 간격으로 실행 가능한 작업을 최대 20개 조회하고 순차 처리한다. 실제 처리 지연에는 앞선 작업 소요 시간도 포함된다.
- 각 작업은 별도 트랜잭션에서 행 잠금을 획득한 뒤 내부 `DELETE /internal/v1/posts/{id}/comments`를 호출한다. 연결 2초, 응답 읽기 3초 제한을 둔다.
- HTTP 실패 시 작업을 보존하고 실패 횟수 및 30초 뒤 재시도 시각을 저장한다. 성공하면 작업을 삭제한다. DB 트랜잭션 실패도 로그를 남기며 미완료 작업은 다음 조회에서 재처리한다.
- 정리 성공 후 응답 유실 또는 작업 삭제 롤백 시 중복 전달될 수 있다. 기존 comment-service의 멱등 닫힘 처리와 생성/닫힘 잠금을 유지했다.
- 삭제 전에 게시물 검사를 통과한 댓글 요청은 정리 전 성공할 수 있다. 이후 정리에서 제거되며, 정리가 끝난 뒤 늦게 도착한 생성은 거부된다. 이미 진행 중인 조회를 취소하지는 않는다.
- 서비스 간 DB/엔티티 공유는 없다. 삭제 후속 작업의 전달 책임을 post-service에 두며, 화면 응답 조합은 Facade에 유지한다.

### 설정 및 제한

- `COMMENT_SERVICE_URL`: 기본 `http://localhost:8084`.
- `post.cleanup.enabled`: 기본 true. 테스트에서는 false로 스케줄링을 멈추고 처리기를 직접 실행한다.
- `post.cleanup.poll-delay-ms`: 기본 5000.
- 현재 H2 메모리 DB와 create-drop은 유지했다. 서비스 재시작 시 게시물·작업·댓글 닫힘 상태가 소실되므로 재시작을 넘는 복구를 보장하지 않는다. 영속 DB 및 마이그레이션이 후속 과제다.
- 게시물 본문은 삭제 상태의 행에 남는다. 보존 기간과 영구 삭제 정책은 미구현이다.
- 재시도 상한은 없으며 실패는 로그와 작업 테이블에서 확인한다. 운영용 알림·관리 화면은 미구현이다.
- 작업 행 잠금 중 HTTP를 호출하는 단순한 방식이다. 대규모 병렬 처리나 작업 임대 방식은 도입하지 않았다.
- 기존 작업 폴더의 JWT·댓글 컨트롤러·팔로우 수정은 보존했다.

### 검증

- 삭제 직후 상세·수정 차단, 목록·개수 제외, 중복 삭제, 타인 삭제 차단.
- 게시물 삭제 상태와 작업의 동시 롤백, 동시 삭제 4건에서 작업 1건 생성.
- 댓글 호출 실패 후 재시도 시각 보존, 조기 재시도 차단, 재시도 성공 시 작업 제거.
- 정리 응답 후 DB 롤백 상황의 재전달.
- 실제 로컬 HTTP 대역으로 내부 DELETE 경로와 503/204 처리 검증.
- 기존 댓글 닫힘 API의 멱등성·늦은 생성 거부·동시 생성 테스트 및 Facade 계약 테스트 실행.
- 실행 명령: `.\gradlew.bat :post-service:test :comment-service:test :facade:test --console=plain`.
- 관련 테스트 66개 통과: post-service 12개, comment-service 5개, facade 49개. 실제 전체 서비스 기동이나 브라우저 E2E 검증은 수행하지 않았다.

## 추가 작업: 사진·동영상 업로드

사용자 요청에 따라 게시글 작성/수정 시 사진과 동영상을 첨부하는 기능을 추가했다. 팔로우 조회 개선보다 먼저 진행했다.

- media-service(8086)를 독립 모듈로 추가했다. 파일은 로컬 디스크, 메타데이터는 서비스의 H2 DB에 저장한다. 파일명은 서버 발급 UUID다.
- JPEG·PNG 사진 10MiB, MP4 영상 50MiB, 게시글당 최대 6개를 지원한다. 사진은 실제 디코딩, 영상은 컨테이너 구조를 검사한다. 동영상 코덱 변환은 하지 않는다.
- 게시글은 `post_media`에 첨부 ID와 순서를 저장한다. Facade가 업로드 회원 상태 및 첨부 소유권을 검증한다. 기존 썸네일 URL API도 유지한다.
- 편집 창에 파일 선택·미리보기·제거·업로드 상태를 추가했다. 재시도 시 업로드가 끝난 ID는 재사용한다. API 모드에서만 파일 업로드를 제공한다.
- 피드는 첨부 보기 버튼을 누르면 인증 fetch로 파일을 받아 사진 또는 재생 컨트롤이 있는 영상을 표시한다. Blob URL은 피드 갱신/편집창 종료 시 해제한다.
- 파일 조회는 게시글 존재와 첨부 관계를 검사한다. 삭제된 게시글 및 제거된 첨부 경로는 404다. HTTP Range/206 응답을 중계한다.
- 실제 HTTP 검증 중 발견한 Gateway의 `.body(null)` 호출도 수정했다. 본문 없는 GET/DELETE에는 body를 설정하지 않으며 회귀 테스트를 추가했다.
- [미디어 도메인 명세](media-domain.md), 도메인 전체 명세, 실행 가이드와 의존성 문서를 갱신했다.

### 제한 사항

- 객체 저장소·CDN·영상 변환/썸네일 추출은 미구현이다. 원본 MP4의 브라우저 코덱 지원에 따라 재생 여부가 달라질 수 있다.
- 업로드 및 조회 프록시는 byte[]를 사용한다. 대용량 동시 전송/스트리밍 최적화는 후속 작업이다.
- 미연결 파일 만료와 파일 영구 삭제는 미구현이다. 게시글 소프트 삭제 시 파일은 보관한다.
- 파일은 디스크에 남지만 메타데이터 H2 DB는 재시작 시 초기화된다. 영속 DB 적용이 필요하다.
- 브라우저 연결 도구가 `The browser access host is unavailable`을 반환해 브라우저에서 직접 재생·레이아웃을 확인하지 못했다. API 검증과 실제 브라우저 재생 검증을 구분한다.
