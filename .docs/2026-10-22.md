# 2026-10-22 개발 상태

## 작업 범위

회원 등록, 로그인, 프로필 조회, 회원 수정, 회원 탈퇴를 구현하고 핵심 규칙을 새 테스트로 검증했다. 기존 테스트는 요구사항의 기준으로 사용하지 않았고, 회귀 확인을 위해 마지막 실행에는 포함했다.

## 구현 상태

| 기능 | API | 성공 상태 | 주요 동작 |
| --- | --- | --- | --- |
| 회원 등록 | `POST /api/v1/users/signup` | 201 | 이메일 중복 방지, BCrypt 해시 저장, 회원 키·등록 시각 반환 |
| 로그인 | `POST /api/v1/auth/login` | 200 | 이메일·비밀번호 검증 후 액세스 JWT 발급 |
| 프로필 조회 | `GET /api/v1/users/{user-key}` | 200 | 공개 프로필 조회, 비밀번호·해시 미노출 |
| 회원 수정 | `PUT /api/v1/users/{user-key}` | 204 | 본인 이메일·소개 수정, 다른 회원의 이메일 사용 금지 |
| 회원 탈퇴 | `DELETE /api/v1/users/{user-key}` | 204 | 본인 회원 데이터 삭제, 이후 조회·로그인 실패 |

- JPA `Member` 엔티티와 `MemberRepository`, `DefaultUserService`를 추가했다.
- 이메일은 소문자로 정규화한다. DB 유니크 제약으로 중복 저장도 방지한다.
- 수정 시 전달하지 않은 이메일·소개는 유지한다. 소개에 빈 문자열을 보내면 내용을 비울 수 있다.
- 이메일 변경 후 기존 이메일로 로그인할 수 없고, 새 이메일로 로그인할 수 있다.
- 잘못된 입력은 400, 로그인 실패는 401, 타인 수정·탈퇴는 403, 없는 회원은 404, 이메일 중복은 409로 처리한다.
- Facade에서 수정·탈퇴 요청의 `X-User-Key`를 user-service로 전달한다.
- Facade에서 하위 서비스의 오류 상태를 보존하고, 유효한 HTTP 상태가 없는 통신 오류는 502로 처리한다.
- 기존 회원가입 통합 테스트의 기대 상태만 새 계약인 201에 맞췄다.

## 문자열 상수 관리 결정

커스텀 HTTP 헤더 이름은 서비스 간 계약이므로 공통 상수로 관리한다.

- `MyHttpHeaders`를 Facade의 `config` 패키지에서 `common-domain`의 `com.petfeed.domain.http` 패키지로 옮겼다.
- 기존 공통 DTO와 같은 공유 계약 모듈에 두어 Facade·Gateway·user-service 사이에 새 의존성을 만들지 않았다.
- Java 최상위 클래스는 `static`으로 선언할 수 없으므로 `final` 클래스, `private` 생성자, `public static final` 필드로 구성했다.
- Gateway·Facade·user-service의 운영 코드에서 `X_USER_KEY`를 사용한다.
- 사용하지 않는 `USER_KEY`는 제거했다. 경로 변수 이름은 HTTP 헤더 상수에 포함하지 않는다.
- 표준 `Authorization` 헤더에는 Spring의 `HttpHeaders.AUTHORIZATION`을 사용한다.
- 오류 메시지, URL 경로, 모든 문자열을 한곳에 모으지 않는다. 같은 의미의 계약을 공유할 때만 상수화를 적용한다.
- HTTP 테스트는 외부 계약 문자열을 직접 사용해 상수 값이 잘못 변경되는 경우도 검출할 수 있게 유지했다.

## 제한 사항과 다음 작업

- 현재 DB 설정은 메모리 H2와 `create-drop`이다. 서비스 재시작 시 데이터가 보존되지 않는다.
- 수정 범위는 기존 DTO의 이메일·소개다. 닉네임·전화번호·비밀번호 변경은 구현하지 않았다.
- 탈퇴는 물리 삭제다. 재가입 제한, 보존 정책, 연관 데이터 정리는 별도 정책이 필요하다.
- 로그인 응답의 `refreshToken`은 `null`이다. 갱신·로그아웃·탈퇴 시 기발급 JWT 즉시 폐기는 구현하지 않았다.
- 수정·탈퇴 권한은 내부 `X-User-Key`가 Gateway에서 신뢰할 수 있게 전달된다는 전제다. 내부 서비스 직접 접근 차단과 헤더 위조 방어를 별도로 검증해야 한다.
- Gateway를 포함한 전체 E2E는 실행하지 않았다. Gateway 기동·JWT 검증·프록시 동작을 검증하는 테스트가 다음 단계다.
- Facade 프로필 조회는 기존대로 post-service의 게시물 수 조회에 의존한다. 이번 H2 테스트는 user-service를 직접 검증한다.
- 게시물·팔로우·팔로잉의 비즈니스 기능은 이번 범위에 포함하지 않았다.

## 오늘의 설계 일기: Facade의 역할과 일관성

### 논의의 출발점

현재 구조가 과도하게 분리된 것은 아닌지 돌아봤다. 이 프로젝트는 MSA와 멀티모듈 학습이 목적이므로, 실행 단위를 줄이는 것만으로 설계를 평가할 수 없다는 점을 확인했다. Gateway와 Facade를 구분한 의도는 공통 진입점의 책임과 여러 서비스를 이용해 요청을 완성하는 책임을 분리하는 데 있다.

### 오늘 정리한 방향

```text
클라이언트 → Gateway → Facade → Feign 통신 어댑터 → 각 서비스
                                                    ↓
                                          도메인·저장소·로컬 트랜잭션
```

- Gateway는 인증과 요청 전달을 담당한다.
- Facade는 요청을 완성하는 데 필요한 서비스 선택, 호출 순서, 독립 호출의 동시 실행, 결과 조합과 전체 실패 대응을 담당한다.
- Feign 어댑터는 외부 서비스의 HTTP API 계약을 표현하고 통신을 수행한다. 독립 서버가 아니라 호출하는 애플리케이션에 포함되는 라이브러리로 분리할 수 있다.
- 이 프로젝트에서는 서비스 간 호출을 Facade에서 조정하고, Feign 사용도 Facade에 한정하는 방향으로 잡는다. 각 서비스는 다른 서비스나 Facade를 직접 호출하지 않고 자신의 업무를 수행한다.
- 각 서비스는 도메인 규칙, 권한 판단, 데이터 변경과 자기 DB의 트랜잭션을 책임진다. 업무 규칙을 Facade로 모두 옮기지는 않는다.
- 기존 MVC 서비스 레이어의 책임 중 유스케이스 전체 흐름을 조정하는 부분이 Facade로 분리된다. 각 서비스 내부의 서비스 레이어는 계속 필요하다.

이는 이번 프로젝트의 학습을 위한 정책이다. 모든 MSA에서 Feign을 Facade만 사용해야 한다는 보편적인 규칙은 아니다. 책임과 호출 방향을 명확히 유지하면서 이 정책의 장단점을 검증한다.

### 동시 실행의 의미

회원 정보와 게시물 수처럼 서로의 결과를 기다릴 필요가 없는 조회는 Facade에서 동시에 시작하고 결과를 모아 응답할 수 있다. 현재의 순차 Feign 호출이 구조 분리만으로 자동 병렬화되지는 않으며, 실행 방식은 별도 구현이 필요하다.

앞 호출의 결과가 필요한 후속 작업은 순차 실행해야 한다. 또한 내부에서 병렬 호출한 뒤 결과를 기다려 응답하는 방식과, 작업을 접수한 즉시 응답하고 백그라운드에서 처리하는 방식은 구분한다.

### 트랜잭션 책임에 대한 결론

단일 애플리케이션에서는 프레임워크에 로컬 트랜잭션의 커밋과 롤백을 위임할 수 있었다. 여러 서비스로 작업을 나누면 요청 전체를 하나의 로컬 트랜잭션으로 묶을 수 없으므로, 전체 작업의 완료 조건과 실패 복구 흐름은 애플리케이션 설계에서 직접 다뤄야 한다.

이는 프레임워크의 트랜잭션 관리를 전부 대체한다는 뜻은 아니다. 각 서비스의 로컬 트랜잭션은 계속 프레임워크에 위임하고, Facade는 서비스 경계를 넘는 작업의 진행과 복구를 조정한다. Facade에 `@Transactional`을 붙여도 여러 HTTP 호출을 원자적으로 롤백할 수 없다.

특히 실패 응답을 반환하는 것과 데이터 일관성을 복구하는 것은 다르다. 다른 호출을 취소해도 이미 완료된 변경은 자동으로 되돌아가지 않는다.

### 생성·삭제·조회에서 어려워지는 부분

| 상황 | 일관성 문제 | 정해야 할 정책 |
| --- | --- | --- |
| 생성 일부 성공 후 후속 작업 실패 | 데이터가 일부만 생성된 상태로 남음 | 완료 조건, 보상 또는 재시도, 중복 생성 방지 |
| 삭제 일부 성공 후 후속 작업 실패 | 일부 데이터만 삭제되거나 참조가 남음 | 삭제 진행 상태, 접근 차단 시점, 재시도·후속 정리 |
| 여러 서비스를 조합해 조회 | 서비스마다 서로 다른 시점의 데이터를 읽을 수 있음 | 허용할 최신성 차이와 응답 기준 |
| 조회 일부 실패 | 필요한 응답의 일부만 확보됨 | 필수·선택 데이터 구분, 전체 실패 또는 부분 응답 |
| 타임아웃으로 성공 여부를 알 수 없음 | 원격 작업은 완료됐는데 응답만 유실됐을 수 있음 | 요청 식별자, 멱등 처리, 상태 확인과 안전한 재시도 |

Facade는 요청 전체의 완료 조건과 복구 절차를 조정하고, 각 서비스는 필요한 로컬 트랜잭션·멱등 처리·상태 조회·보상 기능을 제공해야 한다. 보상은 DB 롤백과 같은 원상복구를 항상 보장하지 않으며, 이미 관찰된 변경이나 되돌릴 수 없는 작업도 고려해야 한다.

오늘의 결론은 Facade가 전체 요청을 조정하는 역할을 명확히 갖는다는 것이다. 그 선택으로 서비스 내부의 책임과 호출 방향은 단순해지지만, 서비스 경계를 넘는 생성·삭제·조회 일관성을 설계하고 검증하는 난이도는 높아진다. 위 내용은 설계 방향을 정리한 기록이며, 병렬 실행이나 분산 작업 복구를 구현했다는 의미는 아니다.

- 위 정책은 앞서 기록한 물리 삭제 구현을 변경할 기준이다. 현재 코드의 소프트 삭제 전환과 작성자 응답 변경은 아직 구현하지 않았다.
- [테스트 책임 정책](testing-policy.md)을 추가했다. 각 서비스는 자신의 업무 규칙을 검증하고, Facade는 호출 조정과 실패 정책을 검증한다. 각 계층의 유닛 테스트 외에 DB·HTTP 계약·E2E 검증을 구분한다.

## 탈퇴 정책 코드 반영

- 회원 탈퇴를 물리 삭제에서 `ACTIVE → WITHDRAWN` 상태 변경으로 전환했다. 회원 식별자·닉네임과 레코드를 보존하며 게시물 서비스를 호출하지 않는다.
- 탈퇴 후 로그인은 401, 공개 프로필·수정·반복 탈퇴는 기존 실패 동작을 유지해 404다. 이메일 유니크 제약을 유지해 탈퇴 이메일 재가입은 409다.
- 내부 작성자 조회 `GET /internal/v1/users/{user-key}/author`는 상태와 표시용 이름만 반환한다. 탈퇴 회원은 `WITHDRAWN`과 `(탈퇴한 회원)`, 정상 회원은 `ACTIVE`와 닉네임을 반환하고 없는 회원은 404다.
- Facade가 회원별 게시물 목록의 각 `PostSummary.author`를 조합한다. 게시물 ID·페이지 정보는 보존한다. 회원 서비스 조회 실패는 오류로 전파하며 탈퇴 상태로 대체하지 않는다.
- user-service에 상태 전환·탈퇴 후 접근 차단·작성자 조회 유닛 검증과 H2 레코드 보존·내부 응답 검증을 배치했다. Facade는 응답 조합·조회 실패·탈퇴 호출 범위를 유닛 테스트하고 WireMock으로 작성자 JSON 전달과 503 전파를 검증한다.
- post-service는 저장소·목록·상세 구현이 없어 실제 게시물 데이터와 작성자 관계 보존, 상세 작성자 응답은 아직 검증하지 못했다. 기발급 JWT 즉시 폐기, 운영 DB 마이그레이션·개인정보 보존 정책, 내부 서비스 접근 통제도 후속 작업이다.
- 기존 작업 중인 `PostFeignClient` 변경은 그대로 보존했다.
- 로그인 이후 클라이언트는 인증 정보를 헤더로 전달한다. 기존 Gateway의 `Authorization: Bearer ...` 검증 및 `X-User-Key` 전달 구조와 Facade의 필수 헤더 계약을 유지했다. 신규 HTTP 테스트도 `X-User-Key`를 포함한다.
- 최종 검증: `.\gradlew.bat :user-service:test :facade:test :api-gateway:test --no-daemon` 성공. user-service 19개, Facade 18개로 총 37개 통과했다. Gateway는 여전히 `test NO-SOURCE`로 컴파일만 검증했다. `git diff --check`도 통과했다. 신규 HTTP 테스트의 헤더 누락과 빈 오류 본문 기대값을 수정한 뒤 최종 통과를 확인했다. 운영 환경·전체 E2E 검증은 수행하지 않았다.

## Facade 목 기반 오케스트레이션 테스트 기본 구성

- `UserFacadeTest`에 `MockitoExtension`, `@Mock`, `@InjectMocks`를 적용했다. Spring 컨텍스트·WireMock·실제 서비스를 기동하지 않는다.
- 기존 3개에 8개를 추가해 11개 시나리오를 구성했다. 프로필과 게시물 수 조합 및 원본 유지, 프로필 실패 시 후속 호출 중단, 게시물 수 실패 전파, 정상·탈퇴 작성자 조합, 커서 전달과 페이지 정보 유지, 빈 목록, 작성자·게시물 조회 실패 전파, 수정 요청자·본문 전달, 탈퇴 성공·실패의 회원 서비스 한정 호출을 검증한다.
- 회원의 권한·탈퇴 상태 판단 자체는 user-service 테스트에 맡긴다. Facade에서는 하위 서비스의 실패를 성공이나 가짜 탈퇴 응답으로 바꾸지 않는지 검증한다.
- 현재 순차 호출과 필수 데이터 실패 시 전체 실패 동작을 기준으로 삼았다. 병렬 실행·타임아웃·분산 쓰기 복구는 구현하지 않았으므로 이 테스트로 검증했다고 간주하지 않는다. HTTP 헤더·경로·직렬화 검증은 기존 HTTP 계약 테스트의 책임으로 유지한다.
- 검증 명령: `.\gradlew.bat :facade:test --tests com.petfeed.facade.UserFacadeTest --no-daemon`. 11개 모두 통과했고 `git diff --check`도 통과했다. 이번 추가 작업에서는 해당 유닛 테스트만 실행했다.

## 정적 팩토리 메서드로 생성 방식 통일

- 공통 요청·응답 DTO에 `@AllArgsConstructor(staticName = "of")`를 적용했다. 전체 필드 생성자는 private으로 생성되고 공개 `of(...)` 메서드로 객체를 생성한다. JSON 역직렬화에 사용하는 기본 생성자는 유지했다.
- 회원 엔티티는 `Member.create(...)`로 생성하고 기존 업무용 생성자를 private으로 변경했다. JPA용 protected 기본 생성자와 식별자·가입 시각·초기 상태 생성 규칙은 유지했다.
- Facade, user-service, 관련 유닛 테스트와 `PostSummary.withAuthor(...)`의 생성 호출을 팩토리 메서드로 전환했다. 외부 라이브러리 타입과 DI 서비스의 생성 방식은 유지했다.
- 검증: `.\gradlew.bat :user-service:test :facade:test :api-gateway:test --no-daemon` 성공. user-service 19개와 Facade 26개, 총 45개가 통과했다. Gateway는 `test NO-SOURCE`로 컴파일만 확인했다. 기존 HTTP 계약·H2 통합 테스트를 통해 JSON 역직렬화와 회원 생성 흐름을 확인했고 `git diff --check`도 통과했다.
